# Database

PostgreSQL 18. **53 tables**, 43 native enum types, 197 foreign keys, 316 indexes
(6 of them partial unique indexes).

Verified with `python scripts/check_schema.py`.

## Conventions

- **UUID primary keys**, server-generated by `gen_random_uuid()` (built into PG 13+).
- **`tenant_id NOT NULL`** on every business table, indexed, `ON DELETE CASCADE`.
  `tenants` is the root and has no `tenant_id` of its own; `permissions` is a
  global catalogue and deliberately has none either.
- **`timestamptz` everywhere**, always aware UTC. Display is IST.
- **`created_at` / `updated_at`** with `server_default=now()`.
- **Soft delete** (`deleted_at`) on records referenced by history — clients,
  documents, engagements. Nothing a filing or an audit trail points at is ever
  hard-deleted.
- **Deterministic constraint names** via a metadata naming convention, so Alembic
  autogenerate produces stable, reviewable migrations.
- **`ondelete="SET NULL"`** for `created_by_id` / `updated_by_id`: removing a staff
  user must never delete the work they were responsible for.

## The person / entity / relationship split

The blueprint is explicit: *"A person may own multiple businesses. Model the
person, legal entity and client relationship separately."*

```
clients               the RELATIONSHIP: manager, risk class, billing
legal_entities        the LEGAL PERSON: individual, company, LLP
client_entity_links   which entities sit in a relationship, and in what capacity
```

One individual owning three proprietaries is **one** client relationship over
**four** legal entities — not four unrelated clients. `client_entity_links` records
the capacity (owner, director, partner, karta, trustee), shareholding and effective
dates.

## Key invariants the database enforces

| Invariant | Mechanism |
|---|---|
| One client code per firm | `UNIQUE (tenant_id, client_code)` |
| One PAN per firm | `UNIQUE (tenant_id, pan)` — a PAN identifies one legal person |
| One registration number per type | `UNIQUE (tenant_id, registration_type, number)` |
| One primary contact per client | partial unique index `WHERE is_primary AND deleted_at IS NULL` |
| **Recurring generation cannot duplicate** | `uq_tasks_template_dedup (template_id, client_id, period_key) WHERE template_id IS NOT NULL AND deleted_at IS NULL` |
| The same, for rule-driven tasks | `uq_tasks_autolist_dedup (compliance_rule_id, client_id, period_key)` |
| One deadline per client/rule/period | `UNIQUE (client_id, compliance_rule_id, period_key)` |
| One filing per client/type/period | `UNIQUE (client_id, filing_type, period_key)` |
| One live assignment per role per task | partial unique index `WHERE is_active` |
| One active deadline override | partial unique index `WHERE is_active` |
| **Separation of duties** | `CHECK reviewer_id <> preparer_id`, `CHECK approver_id <> preparer_id` |
| Internal due date never after statutory | `CHECK internal_due_date <= statutory_due_date` |
| Progress is 0–100 | `CHECK progress_percent BETWEEN 0 AND 100` |
| A verified rule has a verifier | `CHECK deadline_verified = false OR (verified_by_id IS NOT NULL AND verified_at IS NOT NULL)` |
| An override has a reason | `CHECK length(reason) > 0` |
| A skipped step has a reason | `CHECK status NOT IN ('skipped','not_applicable') OR skip_reason IS NOT NULL` |
| A filed record has a date | `CHECK status = 'pending' OR filed_on IS NOT NULL` |
| A decided review/approval has a timestamp | `CHECK ... OR decided_at IS NOT NULL` |
| A refresh token has exactly one owner | `CHECK (user_id IS NOT NULL) <> (client_portal_user_id IS NOT NULL)` |

## Partial unique indexes

Six, and each earns its place:

```
uq_tasks_template_dedup            the idempotency guarantee for recurring work
uq_tasks_autolist_dedup            the same, for rule-driven generation
uq_task_assignments_active_role    one live holder per role per task
uq_deadline_overrides_active       one active override per deadline
uq_contacts_primary_per_client     one primary contact per client
uq_approvals_active_per_type       one pending approval of a type per task
```

## Circular foreign key

`documents.current_version_id → document_versions.id` and
`document_versions.document_id → documents.id` are mutually referential. The model
declares the former with `use_alter=True`, so `create_all` emits it as a separate
`ALTER TABLE`, and the Alembic migration adds it explicitly with
`op.create_foreign_key` after both tables exist. `alembic check` confirms there is
no drift.

## Migrations

```bash
cd backend
python -m alembic upgrade head        # apply
python -m alembic check               # confirm models and database agree
python -m alembic downgrade base      # revert
python -m alembic revision --autogenerate -m "description"
```

Two things the initial migration does that autogenerate alone would not:

1. **Adds the circular documents FK** — autogenerate omits `use_alter` FKs.
2. **Drops the 43 enum types in `downgrade()`.** PostgreSQL does not drop native
   enum types when their tables are dropped, so without this a downgrade → upgrade
   cycle fails with `type "tenant_status" already exists`.

Verified: `upgrade → downgrade → upgrade` completes cleanly.

## What is not in the database

- **Files.** Bytes go to object storage; `document_versions.blob_pathname` is the
  pointer.
- **Secrets.** No plaintext passwords (bcrypt), no raw tokens (SHA-256 digests), no
  integration credentials — those live in environment variables, and
  `integration_connections.credential_ref` holds only a non-secret pointer.
- **Aadhaar.** Deliberately absent; storing it is legally restricted.
